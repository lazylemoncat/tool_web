## 1. 产品定位

### 1.1 一句话定位

Tool Web 是一个 **自用为主, Web-first, 可自部署的个人工具网站**, 在统一的界面和 API 下管理任务, 记账, 专注计时和日历.

### 1.2 动机与目标用户

个人任务, 财务记录, 专注记录和偏好配置分散在不同工具中, 数据难以统一检索和操作; 很多现成工具只面向人工 UI 操作, 缺少稳定的结构化 API. Tool Web 把这些数据统一到同一套结构化模型, 认证和部署流程之下.

| 用户类型 | 定位 |
| -------- | ---- |
| 我自己 | 第一用户, 需求和优先级以自己的日常使用为准 |
| 开发者 (含未来的我) | 需要一个模块边界清晰, API 明确, 可二次开发的代码库 |
| 授权的外部脚本 / Agent | 远期通过受控 API 读写数据, 见 §6, 当前不投入 |

### 1.3 产品不是什么

为避免边界失控, 明确以下限制:

- 不是简历项目, 不为展示而堆功能; 不是商业化产品, 不考虑规模化运营.
- 不内置 AI Agent Runtime, 不内置 Agent 聊天 UI, 不执行外部 Agent 代码.
- 不允许外部调用方直接访问数据库, 只能经过受控 API.
- 不做通用 LLM 编排平台, 插件系统不是近期目标.
- 不以原生桌面端或移动端 App 为主线, 坚持 Web-first.
- 不把富文本页面作为核心数据模型, 优先维护结构化实体.

### 1.4 长期愿景

在现有能力稳定之后, 允许用户授权的外部脚本和 Agent 通过受控 API 操作个人数据 (Agent-ready). 该愿景保留但**不排期**, 详见 §6.

## 2. 设计原则

| 原则 | 含义与当前约束力 |
| ---- | ---------------- |
| Web-first | 浏览器是唯一客户端, 响应式支持 PC / 手机 / 平板, 不做原生 App |
| API-first | 所有能力经 `/api/v1` REST API 暴露, 前端与其他调用方使用同一套接口 |
| Self-hostable | Docker Compose 一键自部署, 敏感配置经环境变量注入 |
| 结构化数据优先 | 核心数据使用结构化模型建模, 不依赖富文本 |
| 模块独立建模 | 文件夹, 标签等按业务模块独立建表建 API, 未经设计文档明确不得跨模块复用 (见 [`AGENTS.md`](../AGENTS.md) 编码规范) |

## 4. 当前限制与已知约束

- 单用户隔离模型: 数据归属基于 `user_id`, 无 Workspace / 协作概念.
- SQLite 单库: 适合个人自部署, 未验证高并发场景; 备份策略待建立 (见 [`roadmap.md`](roadmap.md)).
- 对外 API 暴露自增整数 ID, 未引入 `public_id`.
- 无 API Token / Webhook / 审计日志, 外部调用只能复用用户登录态.
- 前端 lint 存在 baseline 错误, CI 中暂为非阻塞 (见 [`testing.md`](testing.md)).
- 代码层面的坏味道与约定不一致已立案, 见 [`tech-debt.md`](tech-debt.md).

## 5. 非功能需求

| 类别 | 硬约束 |
| ---- | ------ |
| 性能 | 常规 API 响应 P95 ≤ 500ms (复杂查询除外); Todo 基础操作保持轻量; Finance 查询支持按账本/账户/时间范围过滤 |
| 安全 | JWT + httpOnly cookie; bcrypt 密码哈希; 全部业务数据按 `user_id` 隔离; 敏感配置只经 `.env` 管理, 仓库只维护 `.env.example` |
| 可维护性 | 后端路由按模块组织并配套 Pydantic schema 与 pytest; 前端 API 调用统一经 API client 层; `ruff` / `mypy` / `pytest` / `vitest` 通过为合入前提 |
| 可部署性 | Docker Compose 部署可用; 生产配置经环境变量; SQLite 数据文件路径可配置 |
| 国际化 | 新增用户可见文案必须进入 i18n 词典, 不得硬编码单语言; API 返回稳定错误码, 前端负责本地化 |

## 6. 远期愿景: Agent-ready (不排期)

**愿景**: 用户授权的外部脚本 / Agent / 自动化工具, 通过受控凭证 (API Token / Personal Access Token) 和明确权限范围, 经 REST API 或 MCP 风格接口安全地读写个人数据, 关键操作可审计.

**为此保留的设计余地** (现有设计已满足, 无需额外投入):

- API-first: 前端与外部调用方共用同一套 `/api/v1` 契约.
- 统一响应格式与稳定错误码: 外部调用方可依赖.
- 模块独立建模: 未来按模块授权 scope 时边界清晰.
- 结构化数据: Agent 可直接消费, 无需解析富文本.

**显式声明**: 本节内容不进入近期路线图, 不分配工作量. 近期唯一约束是**新设计不得堵死上述方向**. 具体待办 (API Token, MCP Server, Webhook 等) 见 [`roadmap.md`](roadmap.md) 远期区.

## 7. Finance 领域规则

当前已实现并需持续遵守的领域约束:

- 单币种: 每个账本 (ledger) 一种货币, 账户与交易继承账本货币; 不实现多币种和汇率系统.
- 拆分交易: 一笔交易可含多个拆分项 (SplitItem), 拆分项金额之和应与交易金额一致.
- 附件: 附件文件走磁盘存储, 元数据入库并关联交易.

"单币种专业复式记账" 为远期方向, 见 [`roadmap.md`](roadmap.md) 远期区, 当前表结构预留 currency 字段即可, 不做额外设计.
